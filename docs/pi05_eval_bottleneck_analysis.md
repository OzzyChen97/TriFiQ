# pi0.5 仿真评测：瓶颈分析、优化方向与快速评测方法总结

> 基于 2026-08-13/14 在本机（8×A40）完成的 pi0.5 fp16 vs W4A8 全流程评测（RoboCasa365 50 任务×10 trials + RoboCerebra 60 任务×5 trials，每模型 800 episodes）。
> 配套报告: `docs/pi05_fp16_vs_w4a8_eval_report.md`。§6 改进记录涉及的脚本已随收尾清理移除，本文件保留为方法与经验记录。

---

## 1. 瓶颈分析（按实测数据定位）

评测链路 = **评测客户端（mujoco 仿真 + 渲染）→ websocket → 策略服务器（模型推理）**。两端的瓶颈完全不同，且会互相放大。

### 1.1 服务器端：W4A8 推理吞吐是硬瓶颈

| 服务器 | 单请求服务时间 | 吞吐上限 | GPU 利用率 |
|---|---|---|---|
| RoboCasa fp16 (torch.compile) | ~105 ms | ~9.5 req/s | 高（编译后 kernel 密集）|
| RoboCasa W4A8 (eager) | ~900 ms | ~1.1 req/s | **12–40%**（大量时间花在 Python/小 kernel 启动）|
| RoboCerebra fp16 | ~99 ms | ~10 req/s | 高 |
| RoboCerebra W4A8 | ~560 ms | ~1.8 req/s | 20–45% |

W4A8 慢的根因（代码级，详见报告 §4.2）：
1. **量化包 block=16**（目录名误标 b64）：逐块旋转/变换算子数量是 block=64 的 4 倍；
2. **前向结构**：逐块输入旋转 → 激活伪量化 → **fp16 全精度 GEMM**（权重预解量化，不是 int4 kernel）→ 输出旋转恢复——GEMM 与 fp16 同价，其余全是净开销；
3. **eager 执行**（TORCHDYNAMO_DISABLE=1），180 层逐层 Python 开销；
4. **torch.compile 实测无效**（892 vs 897 ms，<1%）：自定义算子打断 dynamo 图。

**结论**：W4A8 单实例 ~1 req/s 意味着 RoboCasa 一个 900 步任务（180 次请求）的纯推理时间至少 2.7 分钟/集；10 trials × 50 任务全部串行的话仅推理就要 ~22 小时。

### 1.2 客户端端：长时 composite 任务的仿真+渲染是第二瓶颈

- 实测每步（mujoco step + 4 次渲染）成本：atomic 任务 ~0.3–0.5 s/步，composite 900 步任务 **~0.8–1.5 s/步**；
- 因此单 episode 时长：atomic ~60–100 s，composite **400–1600 s**；
- 任务时长分布严重不均（composite 是 atomic 的 4–10 倍），**按任务数量均分并行度会造成严重负载不均**（本次 4 路切分按数量均分，导致最后收尾阶段全是 composite 长任务拖尾）。

### 1.3 服务器与客户端串行耦合：排队效应指数级放大

- 协议要求 replan=5（每 5 步请求一次动作块），客户端在推理期间**阻塞**；
- 单客户端实际请求速率仅 **0.15–0.4 req/s**（仿真占大头），远低于 fp16 服务器 9.5 req/s 容量；
- 但 W4A8 服务器容量 1.1 req/s，**2 个客户端同打一台服务器**（需求 ~0.8–1.2 req/s）即接近饱和，排队使每请求等待从 0.9 s 涨到 2.5–2.8 s，单集时长翻倍（实测同一任务 650 s → 1500 s）；
- **教训：客户端数量必须按服务器吞吐配平（需求/容量 < 0.8），而不是按 CPU 核数任意加**。

### 1.4 环境类瓶颈（一次性踩坑）

| 问题 | 现象 | 根因 |
|---|---|---|
| fp16 服务器首请求编译超时 | 首次请求时 websocket 被 1011 断开、客户端崩溃 | max-autotune 编译阻塞事件循环 >20 s，超出 keepalive 超时 |
| 并发 EGL 崩溃 | 14 客户端同时起仿真 → 客户端 SIGSEGV（rc=-11）| 所有 mujoco EGL 上下文默认落在 GPU0（与 vLLM 同卡）→ 显存耗尽 |
| 会话重启杀编排进程 | 后台 job 消失、客户端成孤儿、无人续跑/聚合 | 编排器是 DSH 后台 job，会话重启即被杀；子进程却存活 |
| 时间戳目录碰撞 | 多个并行客户端同分钟完成任务 → 写同一目录互相覆盖 stats.json | 日志目录只到分钟粒度 |
| pkill 自匹配 | pkill -f 把自己的 shell 杀了 | 模式串出现在调用 shell 自身的 cmdline 里 |
| 共享机器干扰 | 中途 GPU6/7 被他人占用、swap 一度 100% | 实验室共享机，无法隔离 |

## 2. 可优化方向（按收益排序）

### 2.1 高收益（下次评测前应做）

1. **W4A8 服务器融合 kernel（Triton）——fast 方案已落地 v1**：变换/量化/恢复融合为 Triton kernel（GEMM 保留 `F.linear` 位级一致），实测单请求 951→435 ms（**2.2×**，2.30 req/s），成功率与 eager 在统计噪声内一致（CloseFridge 冒烟 0.4=0.4）。详见报告 §4.4；更进一步的 3–6× 需要 Triton GEMM（当前未做，需重新数值校验）。
2. **RoboCasa 量化包重新校准 block=64**：与目录名/配方对齐，逐块算子减少 4×；不改代码即可显著降延迟。
3. **任务切分按预估时长均衡**：先按 `get_task_horizon` + 历史单集时长给每个任务估时，再切分到客户端（背包/轮流分配），避免长任务拖尾。
4. **客户端-服务器容量配平**：先测每台服务器单请求服务时间（**间隔请求法**，见 §4.1），再按 `客户端数 ≤ 0.8 × 容量 / 单客户端需求` 分配；排队即加服务器实例或减客户端。
5. **服务器实例横向扩容**：量化服务器吞吐不足时（内存 23GB/卡、A40 46GB），直接多卡多实例（本次 3→4 实例把 RoboCasa 收尾提速 ~3×）——比改代码便宜得多。

### 2.2 中收益（流程层面）

6. **预热流程前置**：fp16 服务器启动后先跑 `warm_pi05_server.py`（容忍首请求编译），避免评测客户端撞上编译墙。
7. **渲染与计算同卡绑定**：客户端 `CUDA_VISIBLE_DEVICES` + `MUJOCO_EGL_DEVICE_ID` 与服务器同卡，避免与其他用户争抢渲染卡（robosuite 要求两者一致）。
8. **日志目录秒级/带 pid 唯一化**：改 main.py 的 `%Y-%m-%d-%H-%M` 为 `%Y-%m-%d-%H-%M-%S`（或加进程号），根除并行覆盖。
9. **trial 级拆分协议**：长任务收尾时按 seed 变体拆成 N×k trials 到多卡并行（本次 5×2 拆分），完成后按日志重建合并 stats.json；注意记录为协议偏差。
10. **编排器用 tmux/setsid 托管 + 可重挂载**：监督器支持从状态文件/结果 JSON 重建断点；RoboCasa 客户端天然幂等（stats.json 跳过），RoboCerebra 按类级 state 文件续跑。

### 2.3 低收益/不建议

11. torch.compile 加持量化服务器：实测无收益（图全被 graph break），除非先做 2.1 的 kernel 融合；
12. 纯增加客户端数：超过服务器容量后只会互相排队，每集时长反升；
13. 换渲染后端（osmesa/软件 EGL）：本环境 PyOpenGL 函数加载失败，且渲染并非主瓶颈。

## 3. 快速评测方法经验总结

### 3.1 规划阶段

- **先做 30 分钟冒烟**：每模型 2 任务 × 2–3 trials，测出"单集时长、单请求延迟、任务 horizon"三个关键数，再算总时长；
- **估算公式**：`总时长 ≈ Σ任务(episodes/task × 单集时长) / 有效并行度`，其中有效并行度受服务器吞吐上限（§1.1）约束；
- **规模权衡**：10 trials/任务（500 episodes/模型）总均值标准误约 ±1.7pp，对"模型级对比"足够；50 trials 主要用于逐任务细粒度结论。先跑 10 trials 出总结论，需要时再补；
- **协议固定**：seed、replan、任务顺序、拆分方式一旦定下，两模型必须完全一致。

### 3.2 执行阶段（分层并行 + 容量配平）

```
服务器层: 每模型 1–N 实例（按吞吐需求），实例数 = ceil(需求/单实例容量)
客户端层: 每实例 ≤ 容量配平的客户端数，任务按预估时长均衡切分、互不重叠
渲染层:   EGL 上下文逐客户端绑定（与服务器同卡），避免集中到一张卡
监督层:   tmux + 可重挂载监督器：心跳、GPU 快照、崩溃重试、断点续跑、完成聚合
```

- 服务器与客户端解耦（websocket），服务器崩溃只需重启服务器（客户端自动重连等待），客户端崩溃由监督器重启（任务级幂等跳过）；
- 瓶颈出现时先判断是**服务时间**还是**排队**（§4.1），再决定"加实例"还是"减客户端"。

### 3.3 监控与诊断

- 每 10 分钟：GPU 快照（利用率 + 显存）、进度心跳（完成任务数/类型数）、端口健康检查；
- 关键判读：
  - 服务器 GPU 利用率 ~100% → 算力瓶颈（fp16 常态）；
  - 利用率低 + 请求延迟高 → Python/eager 开销（W4A8 常态）；
  - 利用率低 + 客户端 CPU 低 + 单集长 → 仿真/渲染或排队；
  - 同服务器双客户端单集时长翻倍 → 排队（需求超容量）；
- 共享机器上：观察 load average、swap、他人在 GPU5/6/7 的作业，必要时换渲染卡或错峰。

### 3.4 收尾与可复现性

- 聚合阶段校验每任务 episodes 数等于协议值（本次 aggregator 的 problems 字段自动查）；
- 所有产物按"模型+协议"分目录存放（日志、rollouts、stats、延迟基准、GPU 快照），报告与聚合 JSON 互链；
- 全部结束后确认进程清零、GPU 释放（本次最终 0 评测进程、GPU 全空）。

## 4. 两个可复用的诊断/操作技巧

### 4.1 区分服务时间与排队时间

背靠背发 N 个请求测到的"延迟"≈ N×服务时间（排队叠加），会误判服务器变慢。正确做法：
- 测服务时间：等服务器空闲时发**间隔请求**（间隔 > 服务时间），取单请求延迟；
- 测排队：背靠背/多客户端并发时再测一次，两者之差即排队贡献。
（本次曾把 0.9 s 服务时间误读为 2.8 s"服务器变慢"，实际是双客户端排队。）

### 4.2 时间戳碰撞防护与重建

- 预防：日志路径精确到秒 + pid；
- 补救（本次用过）：各客户端的逐集结果都在其日志里（`Success: True/False` 行），碰撞后可按日志重建每份 stats 再合并——**客户端日志永远保留逐集成功标记**，这是最后一道保险。

## 5. 一键结论

1. 本次评测最大瓶颈是 **W4A8 服务器推理吞吐（~1 req/s）**，其次是 **composite 长任务的仿真渲染**与**服务器排队放大效应**；
2. 最快见效的优化：多卡多实例扩容 + 按吞吐配平客户端 + 按预估时长均衡切分任务（本次全部验证有效）；
3. 根本优化：W4A8 融合 kernel + block=64 重校准（2–4× 空间）；
4. 流程上最值钱的三个习惯：**预热先行、断点幂等、监控三件套（GPU/心跳/端口）**。
